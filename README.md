# DealWatch MVP

Система поиска недооценённых телефонов на **999.md** + Deal Score + мгновенные алерты в Telegram.

> Цель MVP: ответить на вопрос _«Какое объявление прямо сейчас стоит звонка?»_

## Стек

- Laravel 12 + Inertia + React 19 + Tailwind 4
- SQLite (для старта)
- Очередь (`database`) — сбор и пересчёт выполняются фоном
- Telegram Bot API
- Scheduler: сбор каждые 3 минуты, курсы валют — раз в час

## Быстрый старт (Docker)

На хосте нужен только Docker — PHP, Node и composer живут в контейнерах.

```bash
cp .env.example .env
scripts/dev.sh install    # зависимости, сборка фронтенда, миграции и демо-данные
scripts/dev.sh up         # nginx + php-fpm + обработчик очереди
```

Открой http://127.0.0.1:8000/deals

| Команда                     | Что делает                             |
| --------------------------- | -------------------------------------- |
| `scripts/dev.sh up`         | поднять приложение и очередь           |
| `scripts/dev.sh dev`        | то же + vite с горячей перезагрузкой   |
| `scripts/dev.sh scheduler`  | включить сбор с 999.md каждые 3 минуты |
| `scripts/dev.sh logs queue` | смотреть, что делает очередь           |
| `scripts/dev.sh artisan …`  | любая artisan-команда в контейнере     |
| `scripts/dev.sh test`       | прогнать тесты                         |
| `scripts/dev.sh down`       | остановить всё                         |

Порт меняется переменной `DEALWATCH_PORT`.

Тесты всегда работают с базой в памяти. Если конфиг окажется закеширован
(`bootstrap/cache/config.php`), тестовое окружение не применится — прогон
не начнётся и попросит выполнить `php artisan config:clear`, вместо того чтобы
очистить рабочую базу.

### Развёртывание на сервере

```bash
cp .env.example .env
docker compose -f docker-compose.prod.yml run --rm app php artisan key:generate --show   # положить в .env
docker compose -f docker-compose.prod.yml up -d --build
```

`APP_KEY` обязателен и должен лежать в `.env`: им шифруются сессии и секреты
из админских настроек (ключ OpenAI, токен бота). Ключ, сгенерированный внутри
контейнера, потеряется при пересоздании — поэтому в продакшене контейнер
откажется стартовать без него.

Отличия от локального набора: код и собранный фронтенд лежат внутри образов
(ничего не монтируется), конфиг и роуты кешируются, `APP_DEBUG` принудительно
выключен, логи приложения идут в `docker logs`, база и `storage` живут в
именованных томах, а сбор, очередь и планировщик поднимаются как отдельные
сервисы с `restart: unless-stopped` и health-проверками. Миграции выполняет
только веб-контейнер.

## Telegram

В `.env`:

```env
TELEGRAM_BOT_TOKEN=...
TELEGRAM_CHAT_ID=...
```

Алерты уходят на сделки с verdict `buy` / `check` при первом появлении объявления —
только по частникам (магазины, перекупы и «куплю» не триггерят).
Туда же приходит предупреждение, если сбор с 999.md несколько прогонов подряд пуст.

## Конфигурация

Все числа, влияющие на деньги, живут в [`config/dealwatch.php`](config/dealwatch.php)
и переопределяются через `.env` (полный список — в `.env.example`):

| Группа          | Что задаёт                                                                    |
| --------------- | ----------------------------------------------------------------------------- |
| `economics`     | `prep_cost`, `risk_reserve`, `min_profit` — формула прибыли и потолок покупки |
| `score.weights` | доли компонентов Deal Score                                                   |
| `score.verdict` | пороги `buy` / `check` и жёсткая отсечка                                      |
| `market`        | `buy_max_ratio`, `buy_min_ratio`, минимум выборки, TTL кеша оснований         |
| `sellers`       | сколько активных объявлений делают аккаунт перекупом                          |
| `collector`     | лимит выдачи, политика обогащения карточек, порог алерта о пустом сборе       |
| `stats`         | TTL кеша витринных счётчиков (0 — считать каждый раз)                         |

## Как пользоваться

1. Смотри ленту сделок на `/deals` (score, дисконт, потенциал прибыли).
2. **Открыть** / **Позвонить** — сразу к продавцу.
3. Или вставь URL объявления 999 в поле «Оценить URL».
4. Статусы: `Купил` / `Скрыть` — чтобы не терять фокус.
5. Избранное (`/favorites`) закрывает сделку: покупка → продажа → чистая прибыль.

## Deal Score

Компоненты и веса (`config/dealwatch.php` → `score.weights`):

- 30% дисконт к ожидаемой цене продажи
- 20% потенциальная прибыль
- 12% ликвидность модели
- 12% свежесть объявления
- 8% частник vs магазин
- 8% состояние (оценка по тексту объявления)
- 5% уверенность парсера модели
- 5% уверенность в оценке состояния

Пороги (`score.verdict`):

- `buy`: score ≥ 80 **и** прибыль ≥ 1500 MDL **и** дисконт ≥ 12%
- `check`: score ≥ 60 **и** прибыль ≥ 800 MDL
- жёсткая отсечка: прибыль < 800 MDL или дисконт < 8% → `ignore`

Дополнительно вердикт понижается: цена выше потолка покупки, тяжёлые дефекты,
кликбейт-цена, аккаунт-перекуп, магазин.

Прибыль считается от **ожидаемой цены продажи** этого экземпляра
(рыночный mid минус скидка за состояние минус торг покупателя), а не от «чистого» mid:

```
profit = expected_sale − цена_объявления_MDL − prep_cost − risk_reserve
```

## Важно про парсинг 999

Данные берутся из GraphQL-эндпоинта каталога (`https://999.md/graphql`, подкатегория 40).
Идентификаторы полей (`price` = 2, `body` = 13, `siteModel` = 590 и т.д.) заданы площадкой
и могут смениться без предупреждения — тогда выдача становится пустой, а не ошибочной.
Поэтому:

- пустые прогоны считаются подряд, и после `collector.empty_runs_before_alert`
  прилетает предупреждение в Telegram (`CollectorHealthMonitor`);
- карточка объявления (описание, регион, модель с сайта) открывается **только**
  для новых и изменившихся объявлений — иначе каждые 3 минуты мы бы дёргали
  площадку сотнями лишних запросов (`collector.enrich_new_only`);
- если список пуст — используй **импорт URL** или демо-сид.

Для продакшена следующий шаг: стабильный источник ID (RSS/API/браузерный worker), затем Facebook/Telegram.

## Источники объявлений

`/sources` — что именно DealWatch ищет на 999.md. Категория больше не зашита в код:
можно завести сколько угодно источников и собирать любые товары.

У источника настраиваются:

- **раздел и подкатегория** каталога 999.md (список подтягивается с площадки);
- **ключевые слова** — уходят в поиск площадки (`macbook pro`, `bergamont`);
- **стоп-слова** — объявление отбрасывается, если они есть в тексте («запчасти», «куплю»);
- **границы цены** в MDL и сколько объявлений забирать за прогон;
- **уведомления** и включение источника в расписание;
- **способ оценки**.

### Два способа оценки

| Режим       | Когда                 | Как считается рынок                                   |
| ----------- | --------------------- | ----------------------------------------------------- |
| Телефоны    | источник по мобильным | справочник `market_prices`: модель, память, состояние |
| Любой товар | всё остальное         | медиана цен по объявлениям **этого же источника**     |

Во втором режиме точность зависит от того, насколько узко настроен источник:
«Bergamont Gravel 29» даст осмысленный ориентир, «весь транспорт» — нет. Пока
объявлений меньше `DEALWATCH_GENERIC_MIN_SAMPLES`, карточки честно помечаются
«мало данных», а после сбора источник пересчитывается целиком — иначе первые
объявления так и остались бы без оценки. Цена вдвое ниже нижнего квартиля
источника не даёт вердикт «брать»: сначала «проверь».

Кнопка **«Собрать сейчас»** запускает разовый сбор по одному источнику. Выбор
источника есть и в шапке ленты `/deals`, а со страницы источника ведёт ссылка
на его аналитику — так что смотреть можно и по одной нише, и всё сразу.

## Анализ ниш

`/niches` отвечает на главный вопрос перед тем, как вкладывать деньги: есть ли
в категории оборот и сколько на нём можно заработать.

Ключевой сигнал — не количество объявлений, а **скорость их исчезновения**:
объявление ушло с площадки, значит товар, скорее всего, продан. Чтобы это
измерять, нужна перепись каталога (`php artisan niche:scan`, в шедулере раз в
сутки): обычный сбор берёт только свежие объявления и о старых ничего не знает.
Перепись проходит каталог источника, отмечает, что ещё висит, фиксирует смену
цен, а пропавшее помечает снятым — но только со второй переписи подряд, чтобы
одна неудачная страница не «продала» товар.

**Полный анализ** (кнопка на `/niches` и `/sources`, команда `php artisan niche:full <id>`)
проходит по источнику весь цикл разом: свежие объявления → перепись каталога →
профили продавцов → пересчёт оценок → аналитика. Отдельные кнопки («только
свежее», «только перепись») остаются для точечных прогонов.

Что показывает страница:

- **вердикт ниши** — живая / вялая / мёртвая, с оговоркой «собираем данные»,
  пока наблюдение идёт меньше недели;
- **скорость**: доля ушедших объявлений, медиана дней до снятия, сколько уходит
  за первую неделю;
- **приток и выбытие по неделям** — видно, растёт ниша или затухает;
- **цены**: p25 / медиана / p75, разброс, изменение медианы к прошлому периоду и
  **запас маржи** (купить по нижнему квартилю, продать по медиане, минус издержки);
- **кто торгует**: аккаунтов, доля перекупов и магазинов, объявлений на аккаунт;
- **активные продавцы ниши**: сколько выставили, сколько ушло и за сколько дней —
  видно, кто реально оборачивает товар;
- **перевыставления** — один и тот же товар публикуется снова с того же аккаунта:
  верный признак, что он не продаётся;
- **движение цен** — сколько продавцов снижали цену и насколько;
- **объявления ниши** — весь список источника прямо на странице, с вкладками
  «забирать / смотреть / пропуск», сортировкой по прибыли, score, цене и свежести
  и с пояснением расчёта у каждой строки (чтобы не искать их в общей ленте);
- **подсказки по настройке источника** — если в выборку попали аксессуары
  («батарея для…», «чехол») или цены расходятся втрое, медиана считается по
  разнородным товарам и врёт: страница прямо предложит сузить ключевые слова
  или добавить стоп-слова.

> Обобщённый режим тем точнее, чем уже источник. «JBL Xtreme 3» — хороший
> источник, «jbl» — плохой: в одну медиану попадут колонка, батарея к ней и чехол.

### Что именно продаётся

Прежде чем сравнивать объявление с рынком, DealWatch определяет, **что в нём
вообще продают**: сам товар, запчасти, аксессуар или услугу — и оригинал ли это
(`listings.subject`, `listings.is_replica`, классификатор
[ListingSubjectClassifier](app/Services/ListingSubjectClassifier.php), русский и
румынский).

Без этого «Piese JBL Charge 5-4-6» за 350 лей сравнивается с ценой самой
колонки и выглядит находкой с потенциалом в 1 750 лей, а реплика за 399 —
вдвойне. Поэтому такие объявления:

- **не входят в рынок** — ни в медиану источника, ни в пересчёт `market_prices`;
- **не получают вердикт и потенциал** — только пометку «запчасти / аксессуар /
  услуга / реплика» и объяснение в карточке;
- **считаются отдельно** в аналитике ниши, с подсказкой добавить их слова в
  стоп-список источника.

Учитываются отрицания: «nu a fost reparat» («не был в ремонте») — это описание
товара, а не предложение услуги. Разметить уже собранное:
`php artisan listings:classify-subjects --recalculate`.

### Залежавшиеся объявления

Объявление, которое давно не обновляли, часто уже продано — просто его не сняли.
DealWatch считает дни с последнего обновления на площадке и:

- после `DEALWATCH_STALE_SUSPECT_DAYS` (21) ограничивает score и вешает в карточке
  пометку «без обновления N дней»;
- после `DEALWATCH_STALE_DEAD_DAYS` (60) снимает вердикт «брать» — сначала напиши
  продавцу, потом планируй.

## Мои сделки и отчётность

`/trades` — журнал: что купил, во что вложился, кому и за сколько продал.

- Кнопка **«Купил → в журнал»** на карточке ленты заводит сделку и ставит
  объявление в архив; вручную сделку можно добавить одной строкой.
- В карточке: цена покупки и продажи, произвольные расходы (ремонт, аксессуары,
  дорога), даты, канал продажи, покупатель, заметки и статус
  (планирую → куплено → выставлено → продано / отменено).
- Прибыль считается **с учётом расходов**: `продажа − (покупка + расходы)`,
  рядом ROI и срок оборота в днях.
- Сверху — чистая прибыль, оборот, сколько сделок в работе и сколько денег
  заморожено в непроданных телефонах.

`/reports` — статистика: прибыль по месяцам, разбивка по моделям (средняя
покупка и продажа, маржа, ROI, срок оборота) и по каналам продажи. Период
задаётся датами.

Сделки принадлежат пользователю (`trades.user_id`); закрытые сделки из старого
«Избранного» переезжают в журнал автоматически при миграции.

## Архив объявлений

Объявления на 999.md снимают сразу после продажи, поэтому DealWatch хранит то,
что видел:

- снимок полей (текст, цена, продавец, город) — при первом появлении и при
  каждом изменении цены, для всех объявлений;
- фото и сжатую копию страницы — для «своих» объявлений: избранное, сделка,
  ручной архив (`DEALWATCH_ARCHIVE_MEDIA_SAVED_ONLY=false` включит для всех,
  но на корпусе в десятки тысяч это десятки гигабайт);
- `php artisan listings:check-gone` (в шедулере каждые 6 часов) проверяет
  объявления, которых давно не видно: 404 или «anunțul a expirat» → помечаем
  `gone_at` и сохраняем последний снимок. В журнале такая сделка так и
  подписана: «объявление снято».

## Админские настройки

`/admin/settings` (пункт «Администрирование» в настройках) — ключ OpenAI, выбор
моделей, лимиты расхода, экономика сделки, параметры сбора и Telegram.
Значения хранятся в базе и **перекрывают `.env`**, поэтому продакшен можно
настраивать без правки файлов и перезапуска.

- Раздел видит только пользователь с `users.is_admin` — им автоматически
  становится первый заведённый аккаунт (в сиде это `dealer@dealwatch.test`).
- Ключ OpenAI и токен бота хранятся зашифрованными (`Crypt`), в браузер уходит
  только маска вида `••••••••1234`; пустое поле означает «не менять».
- **Проверить ключ** — обращается к OpenAI и показывает, принят ли он.
- **Обновить список моделей** — подтягивает модели, доступные вашему ключу;
  поля выбора модели превращаются в список с автодополнением.
- Рядом видно, сколько потрачено сегодня и за 7 дней, и сколько осталось до лимита.
- Кнопка удаления секрета возвращает значение из `.env`.

## ИИ-разбор (OpenAI)

Двухуровневая схема: дешёвая модель прогоняет всю выборку и ранжирует её,
дорогая детально разбирает только финалистов — вопросы продавцу, до какой цены
торговаться, что смотреть на месте.

Настраивается на `/admin/settings` либо через `.env` (админка имеет приоритет):

```env
OPENAI_API_KEY=...
OPENAI_MODEL_SCREEN=gpt-5-mini     # скрининг пачки
OPENAI_MODEL_DEEP=gpt-5            # разбор финалистов
DEALWATCH_AI_DAILY_CALLS=200       # предохранители расхода
DEALWATCH_AI_DAILY_COST_USD=5.0
```

Как пользоваться:

- **«Разобрать выборку ИИ»** на `/deals` — берёт текущие фильтры ленты.
- **Поле запроса** — свободный текст: «iPhone 13 128 до 8000, без замен».
  Модель и бюджет сначала разбираются локально (бесплатно), к ИИ обращаемся
  только если своих средств не хватило.

Результат появляется над лентой: сводка, вывод и карточки с приоритетом звонка.
Разбор идёт в очереди, поэтому нужен запущенный `queue:work`.

Настройки из админки (ключ, модели, лимиты) применяются к фоновым задачам
автоматически — перезапускать воркер не нужно. Отчёт о последнем прогоне висит
над лентой сутки; его можно убрать крестиком.

### Разбор конкретного объявления

В карточке каждой сделки есть блок **«Разбор ИИ»** с двумя кнопками:

- **Разобрать текст** — модели уходит полное описание объявления (не обрезанное,
  до `DEALWATCH_AI_DEEP_TEXT_LIMIT` символов) вместе с рыночными цифрами и
  флагами правил. На выходе: дефекты, расхождения с описанием, что спросить
  продавцу, что проверить на встрече и до какой цены торговаться.
- **Разобрать фото** — включаемая функция (`ai.vision_enabled` в админке,
  по умолчанию выключена). Модель смотрит фотографии и ищет то, что не написано
  в тексте: сколы и трещины, вздутие экрана, следы вскрытия, кривые зазоры,
  неоригинальные детали. Каждый дефект помечен источником — 📝 текст или 📷 фото —
  и, где возможно, оценкой влияния на цену.

Фото стоят заметно дороже текста, поэтому запускаются вручную и только для
перспективных объявлений: сначала пачечный разбор отбирает кандидатов, затем
по ним смотрятся фотографии. Количество кадров ограничено
(`ai.vision_max_images`), а если объявление уже в архиве — берутся сохранённые
копии, а не живые ссылки.

**Всё это сохраняется в карточку объявления** (`listing_ai_reports`) и остаётся
там после того, как объявление снимут с площадки.

Что защищает от неприятных сюрпризов:

- в модель уходят только характеристики товара и экономика сделки —
  **телефон и имя продавца не покидают приложение**;
- ответ модели ограничен строгой JSON-схемой (`strict: true`), а не свободным текстом;
- одинаковый вход не оплачивается дважды (кеш на `DEALWATCH_AI_CACHE_HOURS`);
- каждый вызов пишется в `ai_requests` с токенами и стоимостью: `php artisan ai:usage`;
- дневные лимиты вызовов и долларов — при превышении разбор отказывает с понятным
  сообщением, а не молча тратит деньги;
- если ключа нет или OpenAI недоступен, приложение работает как раньше: кнопки
  подсвечивают причину, разбор помечается как неудавшийся.

## Оформление

Приложение работает в светлой и тёмной теме (переключатель в
`/settings/appearance`, по умолчанию — системная). Статусные плашки красятся не
жёсткими цветами Tailwind, а семантическими классами из `resources/css/app.css`:

| Класс                               | Смысл                              |
| ----------------------------------- | ---------------------------------- |
| `surface-success` / `text-positive` | прибыль, «забирать», подтверждения |
| `surface-warning` / `text-warning`  | предупреждения, «смотреть»         |
| `surface-danger` / `text-negative`  | убыток, риск, ошибки               |
| `surface-info` / `text-info`        | справочные блоки                   |
| `surface-ai`                        | всё, что относится к ИИ-разбору    |
| `surface-neutral`, `surface-inset`  | нейтральные и вложенные плашки     |

У каждого класса своя пара значений для светлой и тёмной темы, контраст текста
к фону — не ниже 4.5:1 в обеих. Новые экраны стоит красить этими классами:
`bg-emerald-50 text-emerald-900` в тёмной теме превращается в нечитаемое пятно.

## Производительность

Счётчики ленты и сводка по корпусу считаются одним агрегатом и кешируются
(`stats.cache_seconds`); действия пользователя — «скрыть», «купил», избранное —
сбрасывают кеш сразу, фоновый сбор — по TTL. Основания рынка (`/market`)
кешируются по `market_prices.updated_at`, поэтому пересчёт рынка сам их
инвалидирует, а наблюдения по живым объявлениям обновляются с лагом
`market.evidence_cache_minutes`.

Замеры на синтетическом корпусе 50 000 объявлений (SQLite, до → после):

| Страница                  | Запросов | Время       |
| ------------------------- | -------- | ----------- |
| `/deals`, повторный заход | 17 → 7   | 942 → 59 мс |
| `/deals?sort=model`       | 17 → 7   | 891 → 62 мс |
| `/market`, тёплый кеш     | 19 → 10  | 636 → 6 мс  |
| сводка по корпусу         | 10 → 1   | 551 → 0 мс  |

## Качество

```bash
vendor/bin/phpunit          # тесты (скоринг, оценка состояния, пайплайн, коллектор, UI-роуты)
vendor/bin/pint --test      # стиль PHP
npm run format:check        # стиль фронтенда
npm run lint:check          # eslint
npm run types               # tsc --noEmit
```

Тесты никуда не ходят по сети: `Http::preventStrayRequests()` включён глобально в `Tests\TestCase`.
